Evading Exception & Interrupt Detection

Matthew Dominguez · Oct 25, 2026

Anti-cheat systems for video games have been known to leverage interrupts to detect cheat software for a long time. Some people don't know that they also utilize exceptions for the same purpose. Today, I will explore a way that I have avoided these detection routines, and the implications that these evasion practices carry.

Event Tracing for Windows (ETW) is a feature of Windows that allows a program to gain telemetry on events occurring in real time on the system. Many exception / interrupt handlers on windows trigger some sort of logging with ETW. Anti-cheats have even been seen using function pointer swaps that get called in exception handling paths to get an even lower level hook on global exceptions; an example being the infamous KdTrap hook.

What is the path taken when an exception/interrupt occurs on a core. The machine CPU state is pushed to the stack. Then, the IDTR, which is a register holding the virtual address of your IDT, is read. The IDT is simply a 4kb page that acts as a table to map vector numbers to handlers. The vector number for a pagefault is 14. So in this case, the CPU will find the handlers address in table entry 14 and start execution from there. At this point, the operating system has zero clue an exception or interrupt has occurred. There has been no code ran, between the time the CPU stopped executing and the time that the handler starts executing. This means that if we can find a way to hijack this transition, we can potentially handle our own exceptions and interrupts without notifying the OS.

Overwriting the IDT is not going to work. Not only does PatchGuard (KPP) protect the IDT, but the IDT is a global page; which means the anti-cheat can audit these modifications. How about cloning the IDT to a different page that PatchGuard doesn't monitor, patching our desired handlers, then writing the virtual address of this page to the IDTR. This is a better approach, but there are still some implications that will arise later.

The way that I have defeated exceptions like pagefaults or general protection faults requires two stubs that look like this. 

; rcx: the virtual address of a game page that I am attempting to read from
; rdx: buffer the read data will be written to
safe_copy:
	mov rax, [rcx]
	mov [rdx], rax
	mov rax, 0 ; return success
	ret

abort:
	mov rax, 1 ; return failure
	ret

Now, if a pagefault occurs, in the handler we can simply move the RIP from the safecopy function to the abort function. Which will tell the caller that a pagefault occurred meaning the buffer contains unknown data. Since we handled our own exception, there is no way for the anti-cheat to know anything occurred on the processor. One note to add is that the Control Register 2 contains the virtual address of the last page fault, so maybe clear it in your handler 😛.

This "abort mission" style approach to exceptions is cool, however, there are scenarios where you should not abort mission. Welcome to the stage, the NMI. NMIs are a type of interrupt that is non-maskable. Meaning, "This interrupt will occur right here right now I don't care what you have going on." There are times where NMIs will not run, like if an NMI is already running. Blocking an NMI might be fine, but when the anti-cheat sends 400 NMIs back to back to your core and zero of them run, they will know what is up. People have also tried rerouting NMIs to other cores, which is a funny method that probably worked for a short period of time. Nowadays, the only real viable solution is to let that mother fucker run. How are NMIs used you may ask, well an anti-cheat will register a callback that the NMI handler will execute, which means they literally get to run on your core in your context. They can see your control registers, stack, IDTR, etc. When leveraging our IDT hook, we can first take control of the execution, and write a little context spoofer. Clear sketchy return addresses on the stack, move our instruction pointer out of our driver, and most importantly restore the IDTR. Once we have cleaned up our mess, we will jmp, not call, to the original handler which will eventually run the callback. When they check the state, there will be nothing out of the ordinary.

This is where the big hacker skills come out. What happens when the NMI routine has finished and it's time to IRET? The CPU state that you just spoofed needs to be able to run. Except this time you don't have your IDTR control. Meaning if they send another NMI from this point until the time you can restore your IDTR, you are pants down. The reason I say big hacker skills is because I will unfortunately not be giving any sauce regarding this. There are plenty of ways of working with this, and that is your job to find your own unique method!

Lastly, let's talk about our beloved cli/sti instructions. CLI is our clear interrupt flag (IF) instruction and STI is our set interrupt flag instruction. When you have the interrupt flag cleared, you are no longer allowing for maskable interrupts to run on your core, which includes the Windows scheduler trying to steal your precious execution when it feels like you've had enough time on core.
